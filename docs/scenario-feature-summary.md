# Summary: Сценарии Воспроизведения Угловой Скорости

## Актуализация 2026-06-08

После внедрения удаленного управления production Dashboard-команды проходят через общий `CommandGate`. Для сценарного режима это закрывает ownership remote/local, но не заменяет отдельные сценарные интерлоки: нужно еще явно запретить конфликтующие ручные команды во время активного сценария, движения или stale/offline состояния.

Persistent event journal реализован через `EventLogService` и `C:\NC3\logs\events.jsonl`; для сценариев остается уточнить обязательные события, уровни и retention.

## Актуализация 2026-06-01

Сценарный режим реализован как рабочий runtime, а не как план:

- сценарии хранятся в `C:\NC3\scenarios` в формате `.scn`; базовые файлы для переноса находятся в `scenarios/`;
- UI на вкладке `Угловая скорость` показывает каталог сценариев, позволяет создать, отредактировать, сохранить, удалить и запустить файл;
- `ScenarioFileService` читает/пишет `.scn` через Node-RED file nodes, хранит `global.scenario_files` и `global.scenario_documents`;
- `ScenarioManager` выполняет шаги через существующий путь `CommandHandler -> ELMO XState (UDP) -> ResponseParser`, без отдельного транспорта;
- автосмена диапазона останавливает привод, выполняет `set_resolution`, затем `Drive Init`, после чего повторяет текущий шаг;
- `set_resolution` сохраняет физические `SP/AC/DC` в градусах и пересчитывает их в тики нового разрешения с учетом ограничений;
- timeout достижения скорости стартует после ACK `set_jv` и считается как `abs(targetSpeed)/AC + 10 с`;
- для `low` диапазона фактическая скорость сценария берется из буфера `PX/TM`, а не из raw `VX`;
- `Пауза`, `Продолжить`, `Стоп` и `Аварийный стоп` подключены. `Продолжить` выполняет текущий шаг заново; восстановление остатка выдержки пока не реализовано.

Для стенда кроме `git pull`/переноса `flows.json` и пакета нужно создать или обновить каталог `C:\NC3\scenarios` и положить туда `.scn` файлы. Изменения, сделанные оператором через UI на стенде, не попадут в git сами: их нужно копировать обратно в `scenarios/`, если они должны стать частью проекта.

## Актуализация 2026-05-29

Первая рабочая интеграция сценариев реализована:

- `scenarios/high_resolution.scn`, `scenarios/low_resolution.scn`, `scenarios/range_switch.scn` добавлены как готовые файлы для копирования в `C:\NC3\scenarios`;
- `packages/nc3-elmo-machines/src/scenario.js` парсит формат `.scn`, выбирает диапазон `high/low` с гистерезисом 20 +/- 5 град/с, учитывает пользовательские диапазоны из настроек и допускает +/-5 град/с на границах, кроме абсолютного low-максимума 360 град/с;
- `ScenarioManager` подключен в `flows.json`: UI включает `Работа по сценарию`, выбирает файл, менеджер последовательно отправляет шаги через `set_jv`, переключает диапазон через `set_resolution` + `driveInit` и автоматически вызывает `start_recording`/`record_measurement`;
- признак `Готов` считается по процентной погрешности из основных настроек `settings.general.speedReadyTolerancePercent` и времени устойчивости, выдержка шага начинается только после стабилизации;
- raw data buffer теперь строится из простых `TM/PX` точек ELMO: без усреднения времени и без дополнительных параметров ELMO в data-файле.

Открыто после следующей итерации: partial resume с восстановлением остатка выдержки и расширение существующего `CommandGate` сценарными интерлоками для конфликтующих ручных команд.

## Интерпретация Требований

Из ТЗ следует следующая минимальная семантика сценария:

1. Пользователь включает режим `Работа по сценарию`.
2. Пользователь выбирает сценарный файл.
3. Сценарий состоит из последовательности шагов `скорость + время удержания`.
4. На каждом шаге установка должна:
   - установить новую угловую скорость;
   - дождаться достижения требуемой точности;
   - только после этого начать отсчет времени удержания;
   - по завершении удержания автоматически записать результат в протокол;
   - при включенном флаге `Запись исходных данных` создать data-file длиной, равной времени удержания шага.
5. Если целевая скорость требует смены диапазона энкодера:
   - установка останавливается;
   - выполняется переключение диапазона;
   - выполняется `Drive Init`;
   - сценарий продолжается с текущего шага.

## Что Было Уточнено

Следующие вопросы больше не считаются открытыми и заложены в текущую реализацию:

- критерий достижения скорости: процентная погрешность `settings.general.speedReadyTolerancePercent` плюс время устойчивости `advanced.speedStableTimeMs`;
- таймаут ожидания скорости: от ACK `set_jv`, `abs(targetSpeed)/AC + 10 с`; `advanced.speedReachTimeoutMs` остается fallback/настройкой evaluator-а;
- удержание шага начинается только после стабилизации скорости;
- raw data-файл пишет только временные метки ELMO и углы из `TM/PX`;
- быстрый raw-опрос 30 Гц включается только во время записи и только при включенном флаге записи исходных данных;
- длина буфера/окна записи берется из `hold_sec` шага для сценариев или из `recording_duration_sec` для ручной записи;
- файлы сценариев редактируются в UI и сохраняются в `C:\NC3\scenarios`;
- в `low` диапазоне скорость для `Готов` берется из `PX/TM`-оценки.

Остаются архитектурные вопросы:

- поведение при невозможности выйти на требуемую скорость после ошибки сценария;
- частичное восстановление остатка выдержки после паузы/аварии;
- расширение существующего `CommandGate` сценарными интерлоками для блокировки конфликтующих ручных команд во время сценария.

Это не блокирует реализацию, но эти пункты нужно зафиксировать как параметры или регламент поведения.

## Рекомендуемая Модель Исполнения

Для сценариев нужен отдельный runtime-слой, а не набор разрозненных `function`-узлов.

Рекомендуемая конечная модель:

- `ScenarioManager` как отдельный state machine;
- `scenario_state` в `global context`;
- `scenario_status` в `GlobalStateReader` для UI;
- сценарии хранятся как файлы, а не как inline JSON в flow;
- журнал и протоколирование вызываются автоматически из runtime сценария.

### Состояния Runtime

Фактический набор основных состояний:

- `idle`
- `loading_file`
- `commanding`
- `waiting_ready`
- `holding`
- `range_switch_pending`
- `paused`
- `stopped`
- `emergency_stop`
- `completed`
- `error`

## Расширенный План Реализации

### Этап 1. Файлы Сценариев (реализовано)

Сделать файловый контур сценариев:

- отдельная папка, например `C:\NC3\scenarios`;
- список файлов сценариев для UI;
- чтение выбранного файла;
- парсер формата сценария;
- валидация заголовка и строк данных;
- преобразование значений `градус/с` в тики по текущему разрешению.

Результат этапа:

- UI может получить список сценарных файлов;
- backend умеет загрузить сценарий в нормализованный runtime-формат.

### Этап 2. Runtime Сценария (реализовано)

Добавить `ScenarioManager`, который:

- принимает команды `scenario_load`, `scenario_start`, `scenario_pause`, `scenario_stop`, `scenario_resume`, `scenario_emergency_stop`;
- хранит текущий индекс шага;
- хранит целевую скорость текущего шага;
- хранит состояние таймера удержания;
- инициирует автоматическую запись в протокол по завершении шага.

Результат этапа:

- появляется единая точка управления сценарием;
- сценарий больше не размазывается по UI и `ProtocolManager`.

### Этап 3. Критерий Готовности Шага (реализовано)

Критерий реализован helper-функцией `nc3.evaluateSpeedReady`, которую вызывает `ScenarioManager`:

- получает текущую скорость от `ResponseParser`;
- сравнивает ее с целевой скоростью шага;
- применяет критерий допуска;
- выдает `ready=true/false`.

Параметры: процентный допуск `settings.general.speedReadyTolerancePercent`, время устойчивости `advanced.speedStableTimeMs`, timeout от фактического `AC`.

Результат этапа:

- удержание шага начинается не сразу после команды, а только после фактического выхода в допуск.

### Этап 4. Выполнение Шага (реализовано)

Для каждого шага сценария:

1. Проверить, нужен ли текущий диапазон.
2. Если диапазон не подходит, инициировать технологическую остановку, смену диапазона, инициализацию и возврат к этому же шагу.
3. Подать команду скорости на `ELMO`.
4. Ждать достижения критерия `Готов`.
5. После достижения точности запустить таймер удержания.
6. По завершении удержания автоматически вызвать запись результата.
7. Перейти к следующему шагу.

Результат этапа:

- сценарий выполняется строго по ТЗ.

### Этап 5. Автоматическое Протоколирование (реализовано)

Нужно связать сценарий с существующим механизмом записи:

- при завершении шага вызывать `record_measurement`;
- передавать `duration_sec`, равный `Время_поддержания` текущего шага;
- использовать текущий флаг `Запись исходных данных`;
- при необходимости автоматически открывать протокол в начале сценария.

Рекомендуемое поведение:

- если протокол не открыт, `ScenarioManager` открывает новый автоматически;
- если открыть протокол не удалось, сценарий не стартует.

Результат этапа:

- сценарий сохраняет результаты без ручной кнопки `Запись`.

### Этап 6. UI Вкладки `Угловая скорость` (реализовано)

В UI нужно добавить/довести до рабочего состояния:

- флаг `Работа по сценарию`;
- выбор файла `Сценарий`;
- кнопки `Старт`, `Пауза`, `Продолжить`, `Стоп`, `Аварийный стоп`;
- отображение:
  - текущего шага;
  - общего числа шагов;
  - целевой скорости;
  - фактической скорости;
  - статуса `Ожидание допуска / Удержание / Пауза / Авария / Завершено`;
  - оставшегося времени удержания;
  - текущего имени сценарного файла.

Остается к отдельной доработке сценарная блокировка конфликтующих ручных действий через существующий `CommandGate`:

- ручное задание скорости;
- ручной `JV/JP`;
- ручной запуск движения, если он влияет на тот же канал.

### Этап 7. Диапазоны И Инициализация (реализовано)

Логика сценария должна использовать уже существующий контур:

- определение текущего диапазона из `OL[1]`;
- переключение диапазона через `set_resolution`;
- повторный `driveInit`;
- продолжение сценария с текущего шага.

Это критично, потому что ТЗ прямо требует продолжения сценария после служебной остановки на смену диапазона.

### Этап 8. Аварийная Остановка (реализовано базово)

Это расширение сверх прямой формулировки сценарного раздела ТЗ, но оно необходимо практически.

Фактическая семантика `Аварийный стоп`:

- немедленно отправить команду принудительной остановки на `ELMO`;
- зафиксировать `scenario_state = emergency_stop`;
- заморозить текущий шаг без сдвига индекса;
- сохранить номер шага, целевую скорость, elapsed hold time и причину;
- записать событие в журнал.

Источники аварийной остановки:

- пользовательская кнопка `Аварийный стоп`;
- ошибка `SR`;
- потеря готовности привода;
- потеря связи с `ELMO`;
- нарушение условий безопасности.

### Этап 9. Продолжение Сценария После Аварийной Остановки (реализовано как повтор шага)

Механизм `Продолжить сценарий` реализован как `scenario_resume`:

Предлагаемое поведение:

1. Пользователь устраняет причину аварии.
2. Система подтверждает, что привод снова готов:
   - связь есть;
   - `MO/SO/MS/SR` допускают продолжение;
   - диапазон корректен.
3. При нажатии `Продолжить` сценарий не переходит на следующий шаг, а восстанавливает текущий.
4. Текущая реализация использует `resume_from_step_start`: шаг выполняется заново.

`resume_from_hold_progress` остается отдельной доработкой, потому что для него нужно валидировать качество уже собранного окна измерений и не портить протокол.

### Этап 10. Нормальный Стоп И Пауза (реализовано)

Нужно разделить три разных действия:

- `Пауза`
- `Стоп`
- `Аварийный стоп`

Рекомендуемая семантика:

- `Пауза`:
  - штатная остановка без сброса сценария;
  - runtime переходит в `paused`;
  - допустимо продолжение с текущего шага.

- `Стоп`:
  - штатное завершение сценария оператором;
  - сценарий прерывается;
  - текущий шаг считается незавершенным;
  - дальнейшее продолжение невозможно, только новый старт.

- `Аварийный стоп`:
  - аварийное завершение движения с сохранением контекста восстановления;
  - разрешено `Продолжить`.

## Необходимые Команды ELMO Для Сценариев

Ниже перечислен практический минимум команд, который уже есть или логически нужен в production-flow.

### Команды Управления Движением

- `JV=<ticks_per_sec>`
  - основная команда задания постоянной угловой скорости.
  - сценарный шаг должен опираться именно на `JV`.

- `AC=<ticks_per_sec2>`
  - ускорение выхода на уставку.

- `DC=<ticks_per_sec2>`
  - замедление.

- `BG`
  - запуск движения после задания `JV/PA/PR/JP`.

- `ST`
  - принудительная остановка.
  - базовая команда для `Стоп` и `Аварийный стоп`.

- `MO=1`
  - включение двигателя, если потребуется восстановление после отключения.

- `MO=0`
  - отключение двигателя, если это предусмотрено регламентом конкретного сценарного завершения.

### Команды Для Диапазонов И Инициализации

- `OL[1]=...`
  - выбор пары головок энкодера / диапазона.

- набор команд из `set_resolution`
  - `CA[18]`, `S1[5]`, `KP[2]`, `SD`, `QS`, `VH[1]`, `VL[1]`, `VH[2]`, `ER[3]`, `ER[2]`, `TR[1]`, `TR[3]`
  - используются при переключении диапазона.

- `HM[1]=1`
  - используется в существующем flow для `drive_home`.
  - не является обязательной командой сценарного режима, если не нужен возврат в базовую точку.

### Команды Контроля Состояния

- `MS`
  - состояние движения.

- `SO`
  - статус готовности.

- `MO`
  - статус двигателя.

- `VX`
  - текущая фактическая скорость.

- `PX`
  - текущее положение.

- `JV`
  - чтение текущего уставленного значения сценарного шага.

- `JP`
  - чтение дополнительного параметра профиля, если потребуется в расширении.

- `SR`
  - диагностика ошибок привода.

- `OL[1]`
  - подтверждение текущего диапазона.

### Какие Команды Рекомендовано Использовать В Первой Версии Сценариев

Для первой рабочей версии сценариев достаточно следующего набора:

- `AC`
- `DC`
- `JV`
- `BG`
- `ST`
- `MS`
- `SO`
- `MO`
- `VX`
- `SR`
- `OL[1]`

Если потребуется автосмена диапазонов, тогда дополнительно используется весь контур `set_resolution` и повторная инициализация.

## Риски И Технические Узкие Места

- В ТЗ нет численного допуска для признака `Готов`.
- Нужно избежать конфликта ручных команд и сценарного runtime.
- Нужно правильно разделить `штатную паузу` и `аварийную остановку`.
- Нужно аккуратно реализовать продолжение после автосмены диапазона и после аварии, чтобы не испортить протокол.
- Нужно синхронизировать длительность raw-data окна с `hold_sec` конкретного шага.

## Рекомендуемый Порядок Внедрения
