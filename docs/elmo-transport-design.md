# ELMO Transport + сценарии — дизайн

Статус: проект (анализ перед реализацией). Код `flows.json` по этому документу пока не менялся.
Актуально на: 2026-05-25.

## Цели

1. Убрать TCP race: сейчас на `192.168.1.2:2000` работают **5 независимых `tcp request`** (`CommandHandler`, два `polling ELMO`, `Tilt`, `function 3`), любые два могут перекрыть запрос/ответ.
2. Единственный сериализованный владелец сокета (один in-flight запрос).
3. Динамический период опроса ELMO: от 1 Гц (медленно/покой) до 30 Гц (макс. скорость), 30 точек/оборот при максимальной скорости.
4. Подготовить базу для сценарного режима (Этап 2).

## Этап 1. ElmoTransport (единый сокет + динамический опрос)

### 1.0. Критическая находка: режим завершения `tcp request`

Все текущие `tcp request` работают в режиме `out: "time"` с фиксированным окном `splitc` (100 мс у poll/cmd, 1000 мс у Tilt/function 3): узел ждёт фиксированное время, а не момент прихода ответа.

- poll ограничен ~10 Гц (100 мс/цикл) и добавляет +100 мс латентности к каждой команде;
- **30 Гц в режиме `out:"time"` недостижимы.**

Единый транспорт должен завершать чтение **по терминатору ответа** (`out: "char"` с символом конца ответа ELMO Direct Access — `;` или `CR`), а не по таймеру. Точный терминатор подтвердить на стенде.

### 1.1. Топология

```
CommandHandler ─┐
poll (regular) ─┤
poll (INIT)    ─┼─► [ElmoTransport: очередь + ФСМ] ─► один tcp request (out:char) ─┐
Tilt           ─┤              ▲                                                     │
function 3     ─┘              └─────── ResponseParser ◄─────────────────────────────┘
                                              │
                               drive_state · angle_buffer · события ФСМ
```

Пять продьюсеров перестают держать сокеты: они формируют «конверт запроса» и шлют его в `ElmoTransport` через `link`.

### 1.2. Конверт запроса и очередь

Конверт: `{ id, kind: 'cmd'|'poll'|'tilt'|'init', priority, cmd: "MS;TM;PX;TM;…", expect: 'parse'|'ack' }`.

- **один in-flight**: следующий запрос — только после ответа или таймаута;
- приоритет: `cmd > tilt > poll`;
- дедуп poll: в очереди не больше одного poll;
- **корреляция ответа**: т.к. в полёте один запрос, ответ принадлежит текущему конверту;
- **таймаут запроса** (≈150–200 мс) → событие `ELMO.TIMEOUT` → пометить stale/fault, освободить очередь, продолжить;
- retry: для poll не ретраим (просто следующий tick); для cmd — опционально 1 ретрай.

### 1.3. Состояния ФСМ (весь обмен)

- `offline` — нет ответов N подряд / tcp error;
- `idle` — связь есть, мотор off;
- `ready` — мотор on, готов;
- `sending` — запрос отправлен;
- `awaiting` — ждём ответ; по приходу → dispatch → планирование следующего;
- `init` — `Drive Init` как под-последовательность (временно приостанавливает обычный poll);
- `fault` — ошибка `SR` / таймаут;
- (на будущее) `safety_locked`.

Ключ: poll и команды **не идут параллельно** — оба через одну очередь.

### 1.4. Планировщик опроса (динамика 1–30 Гц)

Формула частоты (30 точек/оборот при макс. скорости, не реже 1 Гц):

```
rate_hz = clamp(|ω_град/с| / 12, 1, 30)
```

(30·(ω/360) = ω/12; при 360°/с → 30 Гц, при ≤12°/с → 1 Гц.)

- **самотактирование**: после диспетчеризации ответа `setTimeout(1000 / rate_hz)` ставит следующий poll;
- `ω` из `VX` (на разгоне можно из уставки), формула в °/с — едина для high/low;
- при команде в очереди poll уступает (приоритет) — временно реже, это нормально;
- во время записи минимальную частоту можно держать по скорости (не занижать искусственно).

Риск: при 30 Гц с одним in-flight каждый round-trip TCP должен укладываться в <33 мс; иначе частота упрётся в RTT.

### 1.5. Интеграция записи

`angle_buffer` по сути не меняется: берёт `tm_us`/`position` из ответов того же транспорта; `TM` остаётся единственным источником времени. При 30 Гц за 60 с — до ~1800 точек (норма), обрезка по `recording_duration_sec`. Таймер записи и `recording_ends_at` от транспорта не зависят.

### 1.6. Миграция по шагам (без поломок)

1. Ввести `ElmoTransport` + один `tcp request` (`out:char`) параллельно старому; проверить poll.
2. Перевести regular poll на транспорт; проверить `angle_buffer`/`drive_state`.
3. Перевести `CommandHandler` (enqueue), удалить его `tcp request`.
4. Перевести `Tilt` и `function 3`.
5. Перевести INIT polling.
6. Удалить старые 5 `tcp request`, оставить один.
7. Включить динамический период.

На каждом шаге — deploy + проверка.

### 1.7. Реализация ФСМ

- Вариант A (рекомендуемый для старта): таблица переходов + очередь в одном function-узле, состояние в `context`/`flow`, без npm-зависимостей и правок `settings.js`.
- Вариант B (XState): `createMachine`/`createActor` через `functionExternalModules`/Setup; actor в `On Start`, `actor.send` в `On Message`, `subscribe → node.send`, `actor.stop()` в `On Stop`. Внешний контракт событий тот же, что у A, — переход на XState не ломает потребителей.

### 1.8. Контракт событий (кратко)

Входы: `UI.CMD`, `POLL.TICK`, `ELMO.RESP`, `ELMO.TIMEOUT`, `INIT.START`, `INIT.STEP_DONE`.
Выходы: `TCP.SEND(cmd)`, обновление `drive_state`, подача в `angle_buffer`, события для сценария/журнала.

## Этап 2. Сценарный режим (ScenarioManager поверх транспорта)

Строится на Этапе 1: все команды движения идут **через `ElmoTransport`**, поэтому сценарий не создаёт собственных TCP-сессий и не конкурирует с poll. Динамический опрос Этапа 1 даёт нужную плотность data-файла на каждом шаге (30 точек/об на максимуме).

Согласовано с `scenario-feature-summary.md` (там детальный пошаговый план и риски) и Приложением А к ТЗ.

### 2.1. Требования из Приложения А

- Режим активируется на вкладке «Угловая скорость»: флаг «Работа по сценарию» + выбор файла в поле «Сценарий».
- Значения скорости из файла устанавливаются последовательно; каждое **поддерживается заданное время после достижения требуемой точности**.
- Воспроизведённое значение скорости **сохраняется в протокол автоматически** (по умолчанию — скорость и погрешность).
- При флаге «Запись исходных данных» одновременно создаётся файл данных; **его длительность равна времени поддержания значения из сценария**; имя файла данных вносится в строку протокола.
- Индикатор «Готов» показывает, что параметры воспроизведения соответствуют требуемым.
- **Автоматическое переключение диапазонов** при выходе значения за текущий диапазон (см. 2.6).

### 2.2. Формат файла сценария (Приложение А)

```
=====
#Идентификатор файла сценария
# комментарий
# комментарий
Имя_параметра1     Значение_параметра1 # комментарий
Имя_параметра2     Значение_параметра2 # комментарий

-------------------

Значение_скорости     Время_поддержания # градус/с    секунды
…
=====
```

Файлы лежат в `C:\NC3\scenarios\*.scn`. Парсер: пропускать `#`-комментарии, читать заголовок до `-------------------`, далее строки шага `скорость[°/с]  время_удержания[с]`. Валидация каждого шага против диапазонов high/low (`drive_limits`).

### 2.3. ScenarioManager как ФСМ

Состояния:

- `idle` — режим выключен;
- `loading_file` — чтение и парсинг файла;
- `ready` — сценарий загружен, ждём «Старт»;
- `running_step` — отправлена команда скорости (`JV`+`BG` через транспорт);
- `waiting_ready` — ждём достижения точности (индикатор «Готов»);
- `holding` — отсчёт времени удержания после «Готов»;
- `recording_step` — авто-запись результата шага в протокол;
- `range_switch_pending` — служебная остановка и переключение диапазона (см. 2.6);
- `paused` / `stopped` / `emergency_stop` / `completed` / `error`.

`scenario_state` в global context: файл, шаги, индекс, целевая скорость/тики, `reached_ready_at`, `hold_started_at`, `hold_remaining_sec`, причина паузы/ошибки, `can_resume`, `auto_protocol_opened`.

### 2.4. Команды и связь с транспортом

- UI → `scenario_load`, `scenario_start`, `scenario_pause`, `scenario_resume`, `scenario_stop`, `scenario_emergency_stop`;
- ScenarioManager → конверты в `ElmoTransport`: `AC`, `DC`, `JV`, `BG`, `ST`, при смене диапазона — `OL[1]` + последовательность `Drive Init`;
- состояние привода (`VX`, `MS`, `SO`, `SR`, `OL[1]`) ScenarioManager получает из событий транспорта/`drive_state`, а не своим опросом.

### 2.5. Критерий «Готов» и удержание

Критерий параметризуемый (в ТЗ численно не задан — открытый вопрос):

- `abs_error_deg_per_sec`, `rel_error_percent`, `stable_time_ms`;
- «Готов» = текущая `ω` в допуске в течение `stable_time_ms`.

Отсчёт времени удержания (`Время_поддержания`) **стартует после «Готов»**, а не сразу после команды. Нужен также таймаут ожидания «Готов» → ошибка/пауза шага.

### 2.6. Автоматическое переключение диапазона (Приложение А)

При значении шага вне текущего диапазона:

1. Остановить вращение (`ST` через транспорт). Показать сообщение о необходимости переключения, **закрыть через 2 с с занесением в журнал**.
2. Команда на переключение пары головок энкодера (`OL[1]`).
3. Команда на инициализацию (`Drive Init`: один оборот для сумматора DSi) — через под-последовательность транспорта (`init`).
4. После успешной инициализации показать сообщение, **закрыть через 2 с с занесением в журнал**.
5. **Продолжить сценарий с текущего значения** (индекс шага не сдвигается).

### 2.7. Авто-протоколирование шага

- если протокол не открыт — ScenarioManager открывает его автоматически в начале сценария (`open_protocol`); если открыть не удалось — сценарий не стартует;
- по завершении удержания — `record_measurement` с `duration_sec = Время_поддержания` шага и текущим флагом `Запись исходных данных`;
- буфер `angle_buffer` за время удержания собирается транспортом по меткам `TM`; data-файл шага имеет длительность = времени удержания;
- по окончании сценария — закрытие протокола (опционально, по регламенту).

### 2.8. UI вкладки «Угловая скорость»

- флаг «Работа по сценарию», выбор файла «Сценарий» (список из `C:\NC3\scenarios`);
- кнопки `Старт` / `Пауза` / `Продолжить` / `Стоп` / `Аварийный стоп`;
- индикаторы: текущий шаг / всего шагов, целевая и фактическая скорость, «Готов», остаток времени удержания, имя файла, статус;
- на время сценария блокировать конфликтующие ручные действия (ручная скорость, `JV/JP`, ручной запуск движения).

### 2.9. Семантика Пауза / Стоп / Аварийный стоп

- `Пауза` — штатная остановка без сброса, продолжение с текущего шага;
- `Стоп` — штатное завершение оператором, текущий шаг незавершён, продолжение только новым стартом;
- `Аварийный стоп` — немедленный `ST`, контекст восстановления сохраняется, разрешено `Продолжить` (в первой версии — повтор текущего шага целиком).

Источники аварии: кнопка, ошибка `SR`, потеря готовности/связи ELMO, нарушение безопасности.

### 2.10. Открытые вопросы (требуют согласования)

- численный критерий «достижения требуемой точности» и таймаут ожидания «Готов»;
- поведение при невозможности выйти на скорость (повтор/стоп шага/стоп сценария);
- авто-открытие протокола, если он закрыт;
- продолжение после аварии: повтор шага vs восстановление остатка удержания;
- единицы скорости в файле сценария (только °/с или также DMS/рад).

### 2.11. Порядок внедрения

- Итерация 1: файловый список + парсер + ScenarioManager (Старт/Стоп) + выполнение шагов через `JV` (на транспорте) + авто-запись в протокол.
- Итерация 2: Пауза/Продолжить, автопереключение диапазона с `Drive Init`, продолжение с текущего шага, UI-статусы.
- Итерация 3: Аварийный стоп и восстановление, таймауты достижения точности, расширенный журнал событий сценария.
