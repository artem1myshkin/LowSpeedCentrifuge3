## Суть проекта

Это проект `Node-RED`, который выполняет роль основного ПК-интерфейса (`ПО АПК`) для управления установкой НЦ-3/2: прецизионной низкоскоростной центрифугой с изменяемым направлением оси вращения. Через этот проект оператор задает режимы работы установки, управляет исполнительными узлами и наблюдает текущее состояние системы.

Основной рабочий поток в проекте: `new ui flow`. Это текущий production-код, с которым нужно работать.

Другие два потока:

- `flow_main` - legacy
- `flow_bep` - legacy

Они сохранены в репозитории как историческая реализация, но в рамках текущей разработки их не используем и не описываем детально.

## Что делает текущий production flow

`new ui flow` собирает в одном интерфейсе управление тремя основными подсистемами АПК:

- `УУВ` - узел управления вращением планшайбы
- `УУН / БУН` - узел управления наклоном оси вращения
- `БЕП` - блоки емкостных преобразователей для контроля положения шпинделя и зазора

По факту текущая реализация решает такие задачи:

- управление угловой скоростью вращения
- управление углом/положением вращения
- управление углом наклона оси
- отображение текущих параметров движения и состояния исполнительных узлов
- прием данных с БЕП, их базовая калибровка и визуализация
- хранение и применение части пользовательских настроек
- двуязычный интерфейс `RU/EN`

## Техническая архитектура

Проект построен вокруг `flows.json` и UI на `Node-RED Dashboard 2.0` (`ui-template` + кастомные Vue/Vuetify-шаблоны).

Основные каналы взаимодействия:

- `TCP` - обмен с контроллерами `ELMO` для управления вращением
- `MQTT` - обмен с `БУН` и `БЕП`
- `exec` - запуск внешнего процесса для `БЕП`
- `file` / `file in` - чтение и запись локальных данных и служебных файлов

По текущему коду и аудиту видны такие интеграции:

- `ELMO` управляется через `CommandHandler`, `ResponseParser` и `tcp request`
- `БУН` использует MQTT-топики вроде `bun_angle`, `bun_systate`, `bun_cmd`, `bun_cmd_setpoint`
- `БЕП` использует MQTT-топики `ch1/data` ... `ch5/data`, `bep/status`, `bep/control`, `bep/write-config`
- для `БЕП` предусмотрен запуск внешнего процесса из Node-RED

## Что важно понимать перед доработками

По аудиту реализации ТЗ от `2026-05-08` проект находится в промежуточном состоянии:

- `26` требований реализовано
- `22` реализовано частично
- `15` не реализовано

То есть проект уже работает как основной операторский UI, но часть требований ТЗ пока закрыта не полностью.

Наиболее заметные ограничения текущей реализации:

- удаленное управление присутствует только частично
- журнал/протокол реализован как заготовка
- формат протокола из Приложения А не доведен до требований ТЗ
- автоматическое выполнение сценариев реализовано не полностью
- часть технологических настроек есть в UI, но не доведена до backend-логики
- алгоритмы расчета поправок и круглограммы для БЕП/наклона пока не реализованы полностью

## Глобальный контекст

В production-flow активно используется `global context`. Ниже перечислены ключи, к которым обращаются UI-компоненты и backend-узлы.

### Состояние `ELMO` / узла вращения

- `drive_state` - последний агрегированный снимок состояния привода, который собирает `ResponseParser`. Это основной источник для `SpeedTab` и `GlobalStateReader`.
- `current_range` - текущее разрешение энкодера: `high` или `low`. Используется для пересчета `тики ↔ градусы` и для записи в протокол.
- `elmo_sample` - последний сэмпл из цикла опроса `ELMO`: время `t`, угол `angle`, позиция `position_ticks`, скорость `velocity_ticks`, текущее разрешение `resolution`.
- `elmo_position_ticks` - последняя позиция `PX` в тиках.
- `elmo_velocity_ticks` - последняя скорость `VX` в тиках в секунду.
- `elmo_angle_deg` - тот же последний угол, но уже в градусах.
- `velocity_setpoint_ticks` - последняя целевая уставка скорости для расчета погрешности в протоколе. Сейчас обновляется при командах `JV/JP` и может использоваться как fallback для `SP`.

Содержимое `drive_state` привязано к реальным командам и ответам `ELMO`:

- `position` - `PX`, текущее угловое положение планшайбы в тиках.
- `velocity` - `VX`, текущая угловая скорость в тиках/с.
- `sp` - `SP`, уставка скорости для позиционных команд `PA/PR`.
- `ac` - `AC`, ускорение.
- `dc` - `DC`, замедление.
- `jv` - `JV`, уставка для режима движения с постоянной скоростью.
- `jp` - `JP`, дополнительная уставка, которую UI теперь также показывает и может отправлять в `ELMO`.
- `ms` - `MS`, состояние движения привода.
- `mo` - `MO`, включение силовой части.
- `so` - `SO`, готовность/servo on.
- `af` - `AF`, состояние удаленного управления.
- `sr` / `sr_status` - регистр ошибок и его декодирование.
- `resolution` - текущее разрешение пары головок энкодера.
- `bun_brake` - состояние тормоза внешней оси `БУН`, читается через `OL[2]`.

### Состояние `БУН`

- `bun_angle` - текущий угол наклона оси вращения, приходит из контура `БУН` и используется в UI и в заголовке файла протокола.
- `bun.mode` - режим legacy-логики `БУН`, встречается в старых участках flow.

### Состояние `БЕП`

- `board_num` - номер платы, с которой работает экран `BEP`.
- `capdac_val` - текущее значение `CAPDAC` для одиночного запуска измерения.
- `values.tilt_curr` - legacy-значение, связанное с экраном калибровки/визуализации.

### Контекст записи протокола

- `protocol_open` - открыт ли сейчас файл протокола.
- `protocol_filename` - полный путь к активному файлу протокола.
- `recording_duration_sec` - длительность окна данных, которое берется для расчета угловой скорости и для файла исходных данных.
- `angle_buffer` - кольцевой буфер последних измеренных углов `{ t, angle }`, который пополняется из `global.elmo_sample`.
- `is_recording` - совместимость со старой логикой записи; после перевода на буфер последних данных не является главным признаком наличия данных.
- `logs` - журнал событий UI, включая открытие/закрытие протокола и результаты записи.

### Настройки и сессия UI

- `settings` - сохраненные настройки интерфейса и алгоритмов. Отсюда берутся язык, периоды опроса и длительность файла данных по умолчанию.
- `activeSession` - текущая активная UI-сессия, используется для арбитража управления.

### Калибровка и служебные коэффициенты

- `use_calib` - флаг применения калибровки.
- `v1_inp`, `v1_out`, `v2_inp`, `v2_out` - базовые калибровочные пары.
- `v1_gap_inp`, `v1_gap_out` ... `v5_gap_inp`, `v5_gap_out` - коэффициенты калибровки каналов `БЕП`.
- `abs_pos_set`, `rel_pos_set`, `vel_set`, `acc_set`, `dec_set`, `jerk_set` - legacy-ключи старой схемы управления вращением; в актуальном `new ui flow` на них опираться не нужно.
